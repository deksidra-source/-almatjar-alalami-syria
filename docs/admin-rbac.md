# مصادقة التاجر وصلاحيات المدير

## نموذج الأدوار

يُحفظ الدور في جدول `users.role` بالقيم `CUSTOMER` أو `VENDOR` أو `ADMIN`. يرتبط كل تاجر بسجل واحد في جدول `vendors` عبر `vendors.user_id`، ويرتبط كل منتج وطلب بالتاجر عبر `vendor_id`. لا يعتمد الخادم على إخفاء الأزرار في الهاتف فقط؛ يجب أن يتحقق من الدور وملكية السجل في كل طلب.

## مسار التاجر

1. يرسل التطبيق طلب `POST /api/auth/merchant/register` يحوي اسم المتجر والبريد أو اسم المستخدم وكلمة المرور.
2. ينشئ الخادم المستخدم بدور `VENDOR` بعد تخزين كلمة المرور على شكل hash قوي، ثم ينشئ سجل `vendors` بحالة `PENDING_REVIEW`.
3. يعيد الخادم جلسة آمنة أو access token قصير العمر، ولا يعيد `password_hash`.
4. بعد تسجيل الدخول يطلب التطبيق `GET /api/merchant/me`، ومنه يحصل على `vendorId` واسم المتجر وحالة الاعتماد.
5. لا تُفتح صفحة المنتجات أو الطلبات أو التحليلات إلا بوجود جلسة تاجر صالحة ومطابقة `vendor.user_id` للمستخدم الحالي.

## مسار المدير

يُمنح دور `ADMIN` يدويًا من قاعدة البيانات أو من لوحة إدارة أولية محمية، وليس من تطبيق الهاتف. تستخدم مسارات الإدارة وسيطًا مثل `requireRole('ADMIN')` قبل تنفيذ أي استعلام. تشمل لوحة المدير قائمة التجار، طلبات اعتماد المتاجر، المنتجات، الطلبات، الإعلانات المروجة، البلاغات، وسجل التدقيق.

## حماية الملكية

مسار التاجر لا يستقبل `vendorId` من الواجهة بوصفه مصدر ثقة. يستخرج الخادم `userId` من الجلسة، ثم ينفذ استعلامًا من نمط `SELECT id FROM vendors WHERE id = $1 AND user_id = $2`. أما المدير فيستطيع إدارة جميع السجلات بعد اجتياز `requireRole('ADMIN')`. يجب تسجيل عمليات الاعتماد والتعديل والحذف في `audit_logs` مع الفاعل والوقت والكيان والتغيير.

## إجراءات الإنتاج المطلوبة

يجب تشغيل الهجرة على PostgreSQL الحقيقي، استخدام HTTPS، تخزين كلمات المرور باستخدام Argon2id أو bcrypt، تدوير الجلسات، تحديد محاولات تسجيل الدخول، وإضافة حماية CSRF إذا كانت الجلسات تعتمد على cookies. شاشة Expo الحالية تنفذ مسارًا تجريبيًا محليًا؛ استبدال التخزين المحلي بمسارات الخادم هو الخطوة المطلوبة قبل الإنتاج.
